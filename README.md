# HTS 301 关税批量查询工具

本地离线批量查询**美国对华 Section 301 加征关税**（中国原产商品）的工具。
输入你的 HTS 编码列表，自动输出：基础税率、301 命中情况与排除、适用 9903 子目、加征比例、FLIP 301 档位与报关标目。
**不含反倾销/反补贴（AD/CVD）**：那是按案件与出口商定税的，不在 USITC 税率表里，结果里会明示「未覆盖」；Section 232 等按产品触发的 Chapter 99 措施也未建模，总税负一栏常驻「不含」说明。

数据全部来自官方原始文件（USITC 全量税率表 + USTR 301 中国清单），**零网络请求、零封 IP 风险**。

提供两种使用方式：**Web 网页版**（推荐）与**命令行版**。

## 功能总览（v1.5）

| 功能 | 说明 | 入口 |
|---|---|---|
| 编码查询 | 输入 HTS 编码批量判定 301 加征（可选手动指定原产地） | Web / 命令行 |
| **多原产地** | 下拉列出**中国**（301 + FLIP 301）、**越南**、FLIP 301 的全部 **60 个经济体**（按经济体查档位与报关标目）、**第二栏国家**（古巴 / 朝鲜 / 俄罗斯 / 白俄罗斯按第二栏税率）、「其他国家（不在名单）」与「**未指定**」（仅 MFN，明示未计入任何原产地措施）。列表来自 `/api/origins`，从数据生成，不再写死。CHN / DEU / 中文名一律归一（DE → EU） | Web「原产地」下拉 / `--origin` |
| **301 flip 历史** | 同一编码**此前的 301 加征档位**（带生效日期），查询展示"此前 X% → 当前 Y%（2026 现行）"；当前值来自 2026 现行 HTS（含 9903.91.xx 2026 档位） | 查询结果「备注」/ 数据结构 `301 flip历史` |
| **FLIP 301 强迫劳动关税** | **2026-07-24 生效**（USTR Final Action FRN 7-23-26）：60 个被调查经济体全部产品加征，**ANNEX II 豁免清单逐编码生效**——**12.5%**（中国/香港/越南/新加坡/巴西等）、**10%**（加拿大/墨西哥/印度/英国等）、net-of-MFN（EU/台湾合计 10%，日/韩/瑞士合计 12.5%）；**已适用 Section 232 的产品豁免**（不重复征税）；不在 60 名单不适用。**档位与报关标目从 `htsdata.csv` 的 9903.05.20–.84 / 9903.06 官方标目推导**（中国 9903.05.31、香港 .43、越南 .84；net-of-MFN 按 MFN 高低落到两个标目之一），手抄 JSON 只作构建时交叉校验；例外标目（在途 / 232 产品 / 民用航空器 / 医药 / USMCA 货等）列在来源弹窗供人工核对 | 查询结果「FLIP301」列（悬停见报关标目）/ `--origin 国家代码` |
| **301 排除（U.S. note 20）** | 命中 301 清单后再判 USTR 排除。排除分两种：**整号排除**（条目正文就是一个统计号，该号下中国产商品全免）→ 直接判免、加征归零、9903 子目改成排除标目、备注写明报关要填哪个号；**按描述排除**（"…(described in statistical reporting number X)"）→ **绝不自动判免**，只列出条目原文、有效期与 Chapter 99 PDF 页码供人工核对。有效期按**查询当天**重算（9903.88.69/.70 均至 **2026-11-09**，.66/.67/.68 已过期；老标目无日期一律按"有效期未标注"不判免）。8 位查询不判免（排除授予到 10 位），但会点名该子目下哪些统计号是整号排除 | 查询结果「301排除」列（可点开条目原文） |
| **ANNEX II 范围限制（Scope Limitations）** | ANNEX II 里 **1257/2113 条通用豁免带范围限制**（Pharma 700 / Aircraft 541 / Ex 16），**只有落在该范围内的商品才豁免**。这类编码不判为"豁免"，而是标 **`+12.5%(范围存疑)`**：税额按**不豁免**保守计（少收会被 CBP 追补加罚），说明栏给出 FRN 页 137 的官方范围定义（`Ex` 档另附 ANNEX II 该行 Description 原文，因为这一档的范围就写在那一栏里），要求人工核实商品用途后确认 | 查询结果「FLIP301」列（琥珀色虚下划线） |
| **加征开关配置** | `measures_config.json` 可分别**启用/禁用** 中国 301 加征（cn301）与 FLIP 301（flip301），默认全启用；禁用后查询/估算/搜索**不含该加征字段、总税负不叠加**，重新启用恢复 | 编辑 `measures_config.json` |
| **来源追溯** | 每条查询结果的每项税负判定均标注**官方出处**（源文件 + CSV 行号 / PDF 物理页码），点击 📄 弹窗展示来源链，可**直接打开源文件并定位到对应页/行**（PDF 用 `#page=N` 定位）；FLIP 豁免同时标注 ANNEX II **范围限制**（Aircraft/Pharma，需按商品描述核对）。弹窗末尾固定两条**边界**：「反倾销/反补贴（AD/CVD）：未覆盖」与「未建模措施（探测）」 | Web「编码查询」结果表「来源」列 / 头部「📄 查看数据来源」 |
| **USITC 官网直达** | 结果表每行 🌐 按钮 / 来源弹窗顶部链接 → 新标签打开 **USITC 官方在线 HTS**（`https://hts.usitc.gov/search?query=<编码>`）直接查该编码最新税率；头部「数据来源」弹窗含官网主入口 | Web「编码查询」结果表 / 弹窗 |
| 税率搜索 | **三通道召回**：关键词（离线）+ 税则行语义（`data/hts_vec.db`，qwen3-embedding:8b）+ CBP 裁定 kNN 投票（`data/cross.db`），按 RRF 融合排序，多通道同时命中的排前面；语义 / 先例通道不可用时自动只剩关键词，页面标明哪条通道未启用。2026-09 实测 26 组常见商品：关键词约 5 组命中，融合后 21 组 | Web「税率搜索」/ `--search`（命令行仍为关键词单通道） |
| 成本估算 | 总税负 = 基础税率（第二栏国家按第二栏）+ 301 + FLIP 301（按原产地与配置开关）；文本常驻「不含 AD/CVD、232 等未建模措施」，命中**仍在执行的**原产地类未建模标目时再标「另有 N 组待核」（已终止的 IEEPA 等不算，见「未建模措施探测」）。编码落在 232 类清单时另给**「232 情形」**（该措施适用、FLIP 按 note 52(f) 免）的数字，见「232 类产品探测」 | Web「成本估算」/ `--estimate` |
| **逐行估算到金额** | 申报清单式表格：**每行自带数量与单位货值**，算出该行货值、综合税负与**预估税费金额**并汇总。单位货值只用于折算从量税——马按头、电池按公斤，全表共用一个单价等于拿电池的公斤价折算马的头价。表内带官方**计量单位**（kg / No. / doz.，来自 HTS `Unit of Quantity`），数量须按该单位填。改数量或单价即自动重算；**合计只累加算得出的行，并注明漏了几行需人工、几行未填**。合计行之下另给**规费**：MPF 0.3464%（每票下限 $33.58、上限 $651.50，整张清单按一票计；USMCA 原产免 MPF 未建模）与海运 HMF 0.125%（「海运」勾选框，非海运不计），FY2026 费率（CBP Dec. 25-10，90 FR 2025-07-23）；规费不是关税，但报关一样要交，此前预估里没有 | Web「成本估算」 |
| **清单归类流式进度** | 后端是**三次批量 LLM 调用**（出词 / 精排 / 写报告）+ 一轮本地召回，不是逐行调 AI，所以不做假的"逐行冒出"动画——四格进度条对应真实走到的那一步（只有召回那格的计数逐行动）。**表格在精排结束就推给前端渲染，不再陪着报告多等一轮**：实测 3 行清单表格 5.6s 到、报告 9.2s 到，可用结果提前约 39% | Web「清单归类」/ `POST /api/ai/analyze/stream`（SSE） |
| **申报底单导入** | 上传 xlsx / csv 自动认列（`税则号列` / `申报数量` / `成交单价` 这类非标准表头也认），回填成清单供人工核对后再算；认不出编码的行单独列出不静默丢弃。另提供 `下载模板` | Web「成本估算」→ 导入申报底单 |
| AI 助手 | 商品归类 / 清单批量分析：召回走同一套三通道（语义与先例通道用原始中文描述），精排候选带归类路径、判定条件与**先例证据**（CBP 裁定票数 + 裁定号 + subject；批量与单条同源）；调用走服务端 JSON 模式、temperature 0 + 固定 seed（可复现）、提示词哈希落盘缓存（`.cache/llm/`，重跑同一清单零等待） | Web「清单归类」/「搜索与归类」 |
| **GRI 逐级归类（升级链）** | 平铺精排是"召回 40 条 → 模型挑"，实测错的多是**方向错**（6 位就错）。逐级链按归类员的顺序做：读**类注/章注/附加美国注释**按 GRI 1 定 4 位品目 → 品目内按 GRI 6 逐级下钻（完整子目树） → 拿 CBP 先例核对（可回退品目或改同品目内的 8 位行，**改判带裁定号展示**）。清单页与单条归类里，平铺置信度低于阈值 / 带存疑 / 无有效结果的行自动升级（`ai_config.json` 的 `guided`，默认关）；搜索页有「📐 逐级归类」按钮直连。结果带「论证」：品目理由、排除了谁依据哪条注、缺什么事实、逐级理由、先例核对。每件 3–4 次调用、约 1.75 万 token，是平铺的 3 倍。实测见「GRI 逐级归类」一节 | Web「搜索与归类」按钮 / 「清单归类」自动升级 / `POST /api/ai/classify/guided` / `eval_classify.py --guided` |
| **本公司先例库** | 审核员在清单行或逐级卡片上点「✓ 采纳」/「✎ 改正」，品名 + 结论 + 理由存进 `data/company.db`（不入 git）。之后：**同品名精确命中直接给结论、不调模型、标「上次这么报的」**；相近品名作为第四条召回通道（权重 4，最高）进候选，精排候选行带「本公司此前申报：…」。同名再记录覆盖旧结论（最新申报口径为准）。这是让工具越用越准的那条路——日常流量多是报过的品类，CROSS 金标测不到它 | Web 清单表 / 搜索页 · `POST /api/company/precedent` · `GET /api/company/precedents?q=` |
| 数据变动提醒 | 官方数据更新重建后自动 diff；Web 进程按数据库文件 mtime 自动换新库，重建后无需重启 | Web「数据变动」 |
| **232 类产品探测** | `scripts/extract_c99_products.py` 从 Chapter 99 PDF 提取按产品触发的 note（16 钢铝铜 / 33 乘用车 / 37 软木 / 38 中重型车 / 39 半导体 / 51 加拿大特定产品）列举的子目清单 → `data/c99_product_scopes.json`，构建时编译进库。编码落在清单里即标「落在 232 类产品清单，该税未计」，且 FLIP 301 按 note 52(f) 对此类产品不适用，FLIP 列标「232 存疑」（税额仍按不豁免计，少收比多收危险）。**「232 情形」列**给另一种情形的数字：构建时把 9903 标目品名里的 `subdivision (g) of U.S. note 33` 解析成 子条 → 标目/税率 映射（`c99_product_headings`），查询命中 note 33 (g) 时给 基础 + 301 + 25%（9903.94.05）、FLIP 免——8507.60 中国产 FLIP 情形 40.9%、232 情形 53.4%，两数并列由人按用途定（note 33(h)：非乘用车/轻卡零件走 9903.94.06 免加征）。有原产地专用标目（英国 9903.94.32 10%、韩国/台湾 15%）时只取专用的；note 16 衍生钢铝铜按金属含量价值计、同子条多档（9903.82.02 +50% / .06 +10%）时只列标目与税率不给整票数字。注意：note 正文不出现 "section 232" 字样，"232" 是按措辞与公告号的推断；清单只是必要条件，note 内另有含量 / 用途 / 技术参数条件 | 查询结果「备注」/「FLIP301」列 / 来源弹窗 |
| **AD/CVD 案件探测** | 反倾销/反补贴按案件 scope（商品描述）与出口商定税，不在税率表里，本工具**不计税**。但案件的参考 HTS 是公开的：从 [ITA ADCVD Proceedings 看板](https://www.trade.gov/data-visualization/adcvd-proceedings)（或 CBP ACE 公开检索）导出案件表，`python scripts/adcvd_import.py 导出表.xlsx` 落成 `data/adcvd_cases.json`，重建后查询时凡编码落在案件参考 HTS（8/10 位精确、4/6 位前缀）内，备注标「⚠ 落在 N 个 AD/CVD 案件的参考 HTS 范围（同原产地 M 个：A-570-xxx …）」，来源弹窗列案号 / 类型 / 国家 / 商品 / 状态。**只探测不判定**：scope 以商品描述为准，HTS 只是参考。未导入时来源栏保持「未覆盖」。ACE 的案件服务（cargo-public.cbp.dhs.gov）2026-09 实测本机连不上，所以是导入不是抓取 | 查询结果「备注」/ 来源弹窗 |
| **评测集** | `scripts/eval_classify.py --build 300` 从 CROSS 镜像抽 2023 年后单编码 NY 裁定做金标（`data/eval/rulings_golden.json`，留一法剔除裁定号本身）；`--build-text` 再抓裁定正文的商品描述段做**正文金标**（`rulings_golden_text.json`，subject 只有 2–3 个词，评归类是猜谜）；`eval_classify.py [--text]` 报各召回通道与融合的 recall@5 / @20，`--llm` 再报归类 top-1 / top-3。改检索、改提示词、换模型先跑它 | 命令行 |
| **未建模措施探测** | `htsdata.csv` 有 636 个 9903 标目，本工具只建模中国 301（84 个）与 FLIP 301（约 100 个）。其余 451 个（note 2 墨加等原产地标目、note 50 巴西、9903.02/.03 转运与全球档、232 类产品标目、配额与保障措施）**不在总税负里**。构建时按组记录每个标目提及的原产地；查询时凡**仍在执行的**标目正文提及该原产地（或以任何国家为条件的 note 2 标目），备注标「⚠ 另有未建模 9903 标目以该原产地为条件，总税负不完整」并在来源弹窗列出示例标目与税率。**只探测不判定**：这些标目的法律状态与是否适用由人核实。**标目状态**：品名里带 `[Compiler's note: provision terminated/expired/suspended]` 的自动判死；官方没标但已不执行的（IEEPA 一族 9903.01/.02 于 2026-02-24 终止、Section 122 的 9903.03.01–.11 于 2026-07-23 到期，Rev18 里既无编者注也无阴影）由 `data/c99_status.json` 按段手工维护，依据只引行政令 / CBP CSMS / 联邦公报。已终止的标目不进备注、不进总税负，只在来源弹窗「已终止措施（不计）」里说明——否则每个原产地每一行都在报警，等于没有警告 | 查询结果「备注」/ 来源弹窗 |
| **Special 栏提示** | 非中国原产地，Special 栏含该原产地对应协定代码（USMCA 的 S、美韩 KR、CAFTA-DR 的 P 等）时给出提示：「符合原产地规则并具备原产地证明时可按此申报」。**只提示不套用**，总税负仍按一般税率 | 查询结果「备注」/「特殊税率提示」字段 |
| **导出带数据版本** | 导出的 CSV/XLSX 每行带「数据版本」：构建时间 + 四份官方源文件哈希前 8 位，转发出去的表格能追溯到税则版本 | Web 导出 |
| 历史记录 | 最近查询本地保存，一键重查 | Web「编码查询」底部 |

> 注：301 flip 历史与 FLIP 301 税率/豁免清单为仓库内**官方数据转录**（`data/flip_301.json`、`data/flip301_forced_labor.json`、`data/flip301_exemptions.json`，后者来自 FRN ANNEX II 逐子目提取），官方数据更新后请按"数据更新方法"重建；缺数据的查询显式标注而非静默空值。

## CBP 裁定先例（`scripts/cross.py` + 归类对比页）

本地税则库的品名文本之外，**类注 / 章注 / 附加美国注释**现已提取进 `data/hts_notes.json`
（供「GRI 逐级归类」读，见下文），但 WCO 解释性注释有版权、仍不在其中——归类卡片底下那句
免责说的就是这条边界。[CROSS](https://rulings.cbp.gov)
是 CBP 自己的裁定库（22 万条、每日增量），写着海关**实际**把什么货判给了什么编码，
往往能直接跨过论证给出答案。围绕它建了一套**三层先例检索**，各层职责不同、可独立降级：

```
   问题形态                          用哪一层                              数据/成本
─────────────────────────────────────────────────────────────────────────────
① 已知编码，要它的全部先例    一期 本地镜像（SQLite 反查）        全量元数据，离线毫秒级
   "8506.50.00 历来判过几条？"   code_precedents() → 精确计数        每晚 launchd 全量刷

② 模糊中文描述，要找相关裁定  二期 语义召回（向量检索）          subject+官方品名嵌入
   "带 LED 的毛绒玩具算哪类？"   semantic_precedents() → 语义近邻    qwen3-embedding:8b 本地

③ 召回到候选，要精读确认      三期 按需深读（AI 读正文）        只拉看过的几条正文
   "这条的货物细节真和我的像吗" deepread_precedents() → 逐字摘录    ollama，用户点击才跑
```

**为什么分三层、而不是一个大向量库**：① 编码反查要的是"全部"和"精确计数"，
向量的 top-k 天生答不了；② 语义召回把 22 万条缩到十几条，③ 这十几条 AI 一次读完，
**不需要预先给全库正文做向量**——向量检索是"读不完才用相似度近似"的妥协，十几条不
需要妥协。于是全量成本只花在零成本的元数据+官方品名上，大模型/正文只花在用户真点开
的那几条。任一层不可用（镜像未建/ollama 离线/CROSS 故障）都静默降级到下一个可用层，
本地税则查询始终是主链路。

Web 入口：「搜索与归类」→ 勾选候选 → 归类对比弹窗底部「CBP 裁定先例」。
打开即自动展示本地镜像的完整反查（①，离线毫秒级）；中文描述可「语义检索」（②）；
召回后点「🔍 深读正文」让 AI 读正文并逐字摘录 CBP 原文（③）。
另有「在线检索」直连 rulings.cbp.gov 作兜底。各块失败只影响自身，本地结果不受影响。
**点裁定号在站内看正文**（`/api/cross/text/{裁定号}`）：正文由服务端从 CBP 拉取并永久缓存
（与深读同一份），按 FACTS / ISSUE / LAW AND ANALYSIS / HOLDING 切段、HOLDING 高亮——
rulings.cbp.gov 是美国政府站，境内直连经常打不开，「官网 ↗」只作备用入口。

**验收（2026-09，全量 221,340 条索引）**：7 组中文查询语义召回 6 组干净命中品目，
「带 LED 灯毛绒玩具」直接捞出 8543+9405+9503 三码并存的一物多号先例。已知弱点：
针织 vs 梭织这类技术属性向量捕捉不到（「羊毛大衣」会返回 6102 针织而非 6201 梭织）——
正因如此才需要第三层深读读正文的 knitted/woven 字样来区分。

### 本地镜像（`scripts/cross_sync.py`，一期）

```bash
python scripts/cross_sync.py     # 全量同步 → data/cross.db（首次 ~5 分钟，69MB）
                                 # 建议 cron 每晚跑一次
```

镜像解决在线 API 做不到的一件事：**某编码的全部先例**。API 的 term 是全文检索，
客户端只能在拉回的前几页里过滤；本地全量 tariffs 索引给出精确计数（实测
8507.60.00 共 80 条、8506.50.00 共 6 条）。建好后归类对比弹窗自动展示完整反查
（离线毫秒级），未建镜像则静默跳过、在线检索仍可用。

- 枚举用 `term=*` + 年度日期切片绕过服务端 10k 深翻页窗口，超限年份自动对半
  细分（1999/2000/2002/2003 实测超限）；起始 1966 年（官方说"1989 至今"，
  实测更早的也在）。约 280 条无日期裁定无法枚举，同步报告里的"差额"即它们。
- **撤销状态每晚全刷**：撤销动的是老记录（N232914 是 2012 年的，2015 年才被
  撤销），增量拉新裁定看不见这种变化。全量元数据仅 ~600 请求。
- 同步报告沿用 build_db 原则：状态变化（现行 → 已撤销）逐条打印，绝不静默。
- **现行税则对账**：裁定引用的编码若已不在今天的 HTS（90 年代裁定 42% 中招、
  2000 年代 28%——税则修订不触发撤销标记），界面上删除线 + ⚠ 标出。
  归类思路可参考，编码必须以现行税则重新落位。

### 语义索引（`scripts/cross_embed.py`，二期）

```bash
python scripts/cross_embed.py            # 全量嵌入 → cross.db 的 vec0 表（~4h，本机 ollama）
python scripts/cross_embed.py --rebuild  # 换模型/换嵌入口径后清空重建
```

把 22 万条裁定的 **subject 嵌入向量**，中文描述直接语义找先例，不再依赖先翻英文关键词。

- 模型 `qwen3-embedding:8b` + 查询侧 instruct 前缀（实测 P@5 0.86，胜 0.6b 的 0.77）；
  MRL 截断存 1024 维（0.9GB，vs 满维 3.6GB），221k 规模 top-50 检索 36ms。
- **嵌入文本 = subject + 编码的官方 HTS 品名**。CROSS 约 2% 的 subject 词不达意
  （"Request for Further Review of Protest..."），但每条都带精确编码、官方品名本地就有，
  拼进去零成本救回：实测一条零产品信号的餐具裁定，查"餐具勺子叉子"从裸嵌入的
  末位（13/13）跳到首位。这比"读全文让大模型生成描述"便宜几百倍，效果相当。
- 每晚 `cross_sync` 后接着跑，只嵌新增（几十条秒级）；`launchd` 已配 `sync && embed`。
- 未建索引 / ollama 离线 → 语义检索降级为提示，编码反查与在线检索不受影响。

### 正文深读（`cross.fetch_ruling_text` + `ai.deepread_precedents`，三期）

语义召回找到"名字像"的候选后，拉这几条的**正文**交给本地大模型精读，指出哪条货物
真的像、并**逐字摘录**决定归类的 CBP 原文。

- 只对召回的前几条**按需拉正文**（永久缓存，正文不可变），不做 22 万全量下载。
  PDF→pdfplumber / OLE2→可打印串提取，探针实测 ~100%。
- AI 角色严格限制在"读 + 定位 + 摘录"，**不改写、不生成归类意见**——先例的价值
  在于能拿 CBP 原话跟海关讲，一经转述就作废。
- **原文校验是安全底线**：AI 引用的句子须逐字出现在正文里（归一大小写/空白/弯引号/
  破折号后子串比对），否则界面标红「引用存疑」。真实验证：读 N286124 判 high、
  摘录 `non-rechargeable ... 8506.50.0000` 逐字命中、校验通过。
- 需配置 AI provider（见「AI 功能配置」）。未配置则深读入口不显示，前两层照常。

例：8506（原电池）vs 8507（蓄电池）的分界是"能不能充电"，本地数据抽不出这个条件，
但 CBP 在 **N286124** 里已明文判过——不可充电锂电池 → 8506.50.0000，
可充电锂离子 → 8507.60.0020。深读（③）读到的正是这条正文里那句原文。

```bash
python scripts/cross.py "lithium primary battery non-rechargeable" --codes 8506.50.00,8507.60.00
```

### 归类召回的三条通道（2026-09）

本地税则的关键词检索是精确匹配：'bluetooth speaker' 在税则里一个词都不出现（官方写
loudspeakers），'电热水壶' 词表没收就是 0 条，'不锈钢菜刀' 命中的第一条是 7204 废碎料。
实测 26 组常见商品，关键词约 5 组命中。现在搜索页与 AI 归类都走三通道 RRF 融合：

```
  关键词  rate.search            离线、确定性，同义词表 + 词干 + 祖先品名
  语义    hts_embed.search_codes  1.1 万条税则行完整品名的向量（qwen3-embedding:8b，18 分钟一次性）
  先例    cross.code_votes        语义召回 20 条裁定按编码投票：撤销不投、按年份加权、
                                 换号按 6 位回退到现行子目（8471.30.00 → 8471.30.01）、
                                 6 位也没了查 data/hs_renumber.json、落不了位的计入「未落位」
```

融合用加权 Reciprocal Rank Fusion（score = Σ w/(60+名次)，w：关键词 0.25 / 语义 1 / 先例 3），
多通道同时命中的自然浮到最前；纯编码前缀查询只走关键词通道。三条都只做**召回**，
候选仍进精排，税率与判定条件仍来自本地税则。建索引：`python scripts/hts_embed.py`
（税则重建后增量只重嵌品名变过的行；`--status` 看状态）。任一通道不可用只影响自己。

**评测（2026-09-15，`eval_classify.py`，300 条 2023 年后单编码 NY 裁定，留一法）**：

| 通道 | recall@5 | recall@20 | 6 位 recall@5 |
|---|---|---|---|
| 关键词 | 0.07 | 0.11 | 0.13 |
| 税则行语义（8b） | 0.31 | 0.50 | 0.40 |
| 裁定先例投票 | 0.71 | 0.79 | 0.76 |
| 等权融合 | 0.60 | 0.77 | 0.66 |
| 加权融合（0.25 / 1 / 3，现行） | 0.67 | 0.82 | 0.74 |

这份金标集的描述来自 CROSS subject，天然偏向先例通道；用户的中文口语描述上语义通道更重要

### GRI 逐级归类（升级链，2026-09-16）

**问题**：换更强的模型做平铺精排，60 条正文金标 top-1 从 43% 到 58%，但错的 25 条里 23 条是
**6 位就错**（品目方向错），且模型错时的置信度与对时几乎一样（0.84–0.87 vs 0.94，无一条低于 0.6），
靠"模型自己发现不对"再查是不成立的。归类员不这么干：先读注释排除，按 GRI 1 定品目，再在品目内
逐级下钻，最后拿先例核对。`scripts/guided.py` 把这个顺序做成固定工具链，模型每步只做那一步的判断：

```
① 品目（GRI 1）  召回候选按 4 位品目分组 + 涉及章的全部品目 + 类注/章注/附加美国注释（data/hts_notes.json）
                 → 排序的品目（≤2）、排除了谁、依据哪条注、缺什么事实；正确品目在未列出的章可点名，补注释重判一次
② 下钻（GRI 6）  该品目的完整子目树（缩进，叶子带税率）+ 附加美国注释 → 8 位行 + 每层理由
                 code 不在树里重问一次，再无效**报错不兜底**（不退回某个候选）
③ 先例           拟定编码的历史先例（按码反查）+ 语义最近的先例 + ≤2 条正文 → 一致与否；
                 可回退到另一品目（再下钻一次）或改同品目内的 8 位行；改判带裁定号与理由，界面上必须看得见
```

**实测（gpt-5.6-luna，正文金标，留一法）**：

| 集合 | 品目对 | 下钻后 8 位对 | 最终 8 位对 | 6 位对 |
|---|---|---|---|---|
| 平铺做错的 21 条（23 条去掉 2 条噪声） | 10 | 6 | **7** | 8 |
| 平铺做对的 15 条对照 | 14 | 12 | **14**（坏 1） | 14 |

救回的 7 条里 4 条是品目方向纠正（2933→2939、3822→3824、3926→9404、3004→2933），1 条金标根本不在
平铺的 40 条候选里（模型从章的品目清单里自选了 3824）。先例步共改 5 条：救 3、坏 1、无变化 1——净正但有波动，
所以改判不静默替换。剩下的品目错里 9/11 金标所在章已在展示的注释里，模型是看见了判错（4 条引注释把金标品目
明确排除，多条自己列了"缺事实"），CBP 手里有样品、模型只有 300 字，这类错更多检索救不回来。
**集成版 60 条整体（2026-09-16，平铺默认推理 + 阈值 0.9 自动升级）**：top-1 **39/60（65%）**、top-3 46（77%）、
6 位 top-1 40；对照平铺基线 35 对：新救回 7、做坏 3、净 +4。升级了 25 行（42%，比预估的三分之一多），其中最终对 12；
升级行里品目步对 15、下钻后对 11、先例改判救 2 坏 1。做坏的 3 条全在升级行（干菌丝体 1404→0602、加糖饮料 2202.10→2202.99、
钓具 9507.10→9507.90），是逐级链自身的判断错，不是接线问题。样本 60 条，1 条 1.7 个百分点。

**成本与开关**：每件 1.6–1.75 万输入 token、45–50 秒，平铺是 5.4 千、27 秒，约 3 倍。所以不全量跑：
`ai_config.json` 的 `guided: true` 只对**平铺置信度 < guided_threshold（默认 0.9）/ 带存疑信号 / 无有效结果**
的行升级（实测 0.9 时约三分之一的行升级，其中七成确实是错的）；`guided_effort` 单独设升级链的推理强度
（平铺可设 `reasoning_effort: none` 提速，升级链保留推理：实测关推理 top-3 持平、top-1 低 8 个点）。
**默认关**：它需要强模型，qwen3:8b 这类本地小模型跑不动 1.3 万 token 的注释提示；Ollama 上必须设
`num_ctx ≥ 16384`，否则 Ollama 会静默截掉提示末尾——恰是注释那段——`guided.classify_guided` 会直接拒绝。
Web「AI 服务配置」面板可勾选。

**注释数据**：`python scripts/hts_notes.py` 从 USITC 各章 PDF（缓存 `.cache/hts_chapters/`）提取全部 96 章
的类注、章注、附加美国注释与统计注释 → `data/hts_notes.json`（入 git，526KB，`meta.release` 记录抓取时的
HTS 版本；2026-09-16 为 Rev19，税则数据为 Rev18，年内注释基本不变）。HTS 修订后重跑一次。缺这份文件时
逐级链照跑，但结果标「注释缺席」。

**评测**：`python scripts/eval_classify.py --text --guided --limit 60` 每条强制走逐级链，另报品目对 / 下钻对 /
先例改判救几坏几；`--llm` 不加 `--guided` 则按配置对低置信度行升级，与线上一致。留一法把裁定号从召回投票和
逐级链的三条先例路径（按码反查 / 语义 / 正文）里全部剔除。

### 65% 之后：剩下的错在哪，四个方向（2026-09-16）

集成版 60 条剩 21 条错，拆开：**8 条正确答案根本不在 40 条候选里**（三条召回路前 20 名全无，连 6 位都对不上）、
**5 条平铺很自信（≥ 0.9）没升级但错了**（3 条化工品）、**7 条升级了但逐级链自己判错**（多数缺决定性事实）、1 条超时。
对应四件事，都已落地或可跑：

1. **升级触发规则**。升级的行带「升级原因」。同一批 60 条、同一留一法、平铺全命中缓存，对照现行（阈值 0.9、无规则）：

   | 触发方式 | 升级行数 | top-1 | 对照现行 39 对：救 / 坏 |
   |---|---|---|---|
   | 阈值 0.9（现行） | 25 | 39 | — |
   | 阈值 0.95 | 34 | 37 | 0 / 2 |
   | 0.9 + 化工章（28–38）一律升级 | 32 | 40 | 1 / 0 |
   | 0.9 + 前三候选跨章一律升级 | 36 | 38 | 0 / 1 |

   结论：**单纯提阈值是负收益**——多升级的 9 行一条没救回、多坏 2 条，那 5 条"自信地错"即使升级逐级链也判不对；
   化工章规则保留（`guided_force_chapters` 默认 `28-38`），跨章规则默认关（`guided_cross_chapter`，跨章分歧更适合
   辩论式核对而不是再跑一遍同一条链）。升级信号的根本问题是模型自报置信度不可靠，下一步用"两个模型是否一致"替代。
2. **召回上限**：三件独立的事，各自先在 295 条召回评测上量（`eval_classify.py --text [--rewrite]`，报 r@5 / r@20 / r@40，
   r@40 是精排能看到的上限；2026-09-16 现行基线：关键词 0.01 / 语义 0.55 / 先例 0.80 / 融合 **0.84**）。
   - 英文 subject 改写（`recall_rewrite`，**默认开**）：出词之外单独一个几十 token 的小调用，让模型把描述写成一句
     CBP 裁定 subject 风格的英文，语义与先例通道各跑两路查询、通道内按每个编码的最好名次合并（`rate.merge_ranked`），
     通道权重不变。清单模式一次批量调用。295 条实测：语义 r@40 0.55→0.59，先例 r@5 0.69→0.73、r@40 0.80→0.83，
     融合 r@20 0.81→**0.84**、r@40 0.84→**0.87**（r@5 0.64→0.61，前排略挤，但精排看的是前 40）。
   - 税则行文档扩展（`python scripts/hts_embed.py --expand`，**当前索引已带**）：每个 8 位编码的嵌入文本拼上最近 8 条判到它的、
     未撤销裁定的货物名（去"The tariff classification of"套话、去产地），6671 行拼上了、用到 2.6 万条裁定。
     **评测金标里的 300 条裁定自动排除**，否则语义通道的数字是假的。文本哈希变化触发全量重嵌（8b 约 20 分钟），
     `--status` 里 `expansion` 标明当前索引是否带扩展。295 条实测（在改写之上）：语义通道 r@5 0.31→**0.39**、
     r@20 0.48→**0.61**、r@40 0.59→**0.68**；融合 r@5 0.61→0.63，r@20 / r@40 持平 0.84 / 0.87——语义通道多召回的
     这批金标先例通道本来就有（两者同源于裁定），融合上限没再抬。它的价值在先例通道不可用、或用户中文口语描述
     （这份金标测不到）的场景。融合权重按各通道前 20 名做离线扫描，(0.25, 1, 3) 与其它组合无差别，未动。
   - 先例通道第二个向量（`python scripts/cross_desc.py fetch` → `embed`）：2015 年后未撤销带税号的 NY 裁定约 2.8 万条，
     逐条抓正文取"申请人描述的货"那一段（与正文金标同一套抽取，永久缓存），嵌进 `cross.db` 的 `vec_desc`；
     `semantic_precedents` 同时查 subject 向量与描述段向量，同一裁定取更近的。抓取约 1 条/秒、可中断续跑，
     `status` 看覆盖率。295 条实测（先例通道 r@5 / r@20 / r@40）：无描述段 0.73 / 0.81 / 0.83 →
     首批 6341 条（2023-06 起）0.75 / 0.83 / 0.85 → **全量 23,657 条（2026-09-16 抓完）0.76 / 0.84 / 0.86**；
     融合 r@5 0.63→**0.66**、r@20 0.84→**0.87**、r@40 0.87→**0.90**。三项召回改动累计：融合 r@40 **0.84 → 0.90**。
     全量 2.47 万条符合条件的 NY 裁定里 95% 抽到了描述段，之后由夜间任务增量。
3. **逐级链判断——同级对证 + 按需先例正文**（2026-09-16 深夜）。剩下的错多是"正确答案在候选里却没挑中"，
   其中同品目内的错集中在"具名子目 vs Other"之间。加了两件事：
   - **按需取先例正文**（`cross_desc.precedent_examples` / `descriptions_for`）：候选编码各反查最近几条未撤销裁定，
     库里没有描述段的当场拉正文抽取、落库并嵌入 vec_desc——索引随真实使用自己长，每次查询网络请求封顶 12 次、
     永久缓存。这是"查询时才取正文"的做法，但触发条件不是"觉得不对"（模型发现不了自己错），而是对每个候选都看一眼
     海关实际判进去的货。
   - **同级对证**（`guided._step_verify`，下钻之后、先例之前多一次调用）：同一父节点下的每个子目列出条文 + 海关实际判进
     该行的货物描述，模型逐条标"满足 / 无证据 / 矛盾"并引用描述原文，再给最终编码（只能在同级里改）。"无证据"的条件
     直接进「需确认」。先例核对步同样换成带货物描述的先例。`guided_max_calls` 默认提到 8。
   **结果（同一批 60 条，对照上一轮最终配置的 39 对）**：top-1 **42（70%）**、top-3 48（80%）、6 位 43；新救回 3、做坏 0；
   升级 23 行里最终对 15（上一轮 13）。归因要说清：**同级对证这一步在 23 行里一次都没改判**（全部维持下钻所选），
   它产出的是 12 条"无证据"的条件进了「需确认」；救回的 3 条来自裁定描述段索引从 6.3 千条长到 1.1 万条后候选池的变化
   （珠宝盒那条正是"摘要不像、正文像"的例子，进池后逐级链就选对了），以及先例核对步换成带货物描述后把干菌丝体判回 1404。
   也就是说这一轮的收益主要来自"拿正文而不是摘要"，对证步是零改判、零做坏、多了结构化的问题清单。
4. **补事实**：链里产出的「缺事实 / 需确认」在搜索页逐级卡片与清单页论证弹窗里都变成一个输入框，写一句核实到的事实
   「补充后重跑」——整条链带补充说明重走一遍（约 1 分钟），补充内容记进结果供审计。这是唯一能把"描述里没有"的错变对的办法。
5. **本公司先例库**（`scripts/company.py`）：审核员每次「采纳」/「改正」存一条（品名、描述、最终编码、原产地、理由、时间），
   `rate.hybrid_search` 把它当第四条通道（`company`，权重 4）。品名归一后精确一致 → `classify_product` /
   清单模式直接给这条结论、不调模型、不升级，标「公司先例」；子串与向量近邻（同一嵌入模型，≥ 0.6）进候选池并在精排候选行里
   标「本公司此前申报」。`HTS_RECALL_CHANNELS` 去掉 `company` 可关。库为空时通道静默为 0 条。
   **历史申报入库前必须先对账**（`scripts/audit_company.py`）：先例库权重最高且同名直接出结论，报错的那条进去就会被
   稳定地重复下去、连被质疑的机会都没有。顺序是**对账 → 人工过分歧 → 确认的才 `record()`**。对账纯本地、不调模型，
   几千条几秒钟，查七类：8 位不在现行税则 / 10 位统计后缀已作废（报关会退单）/ 基础税率与 general 不符 /
   DUTY 里折进了 301·FLIP（与「总加征」重复计算的风险）/ 复合税只存了从价部分 / 材质与编码的材质支不符
   （第十一类注释 2 按重量占优；含聚氨酯时顺带提示第 59 章注释 2 那条路）/ 申报品名与子目条文的品类冲突
   （"毛衣"报在"Skirts and divided skirts"下）/ 低税率的具名天然纤维行 + 异常低单价（**只标风险不判对错**，
   纤维成分要第三方检测报告，是 CBP 实验室抽检的常规项目）。
   ```
   python scripts/audit_company.py 申报数据.json --md 报告.md --json 明细.json
   ```
   吃 `.json`（对象数组）/`.csv`/`.xlsx`，列名按别名表自动认，认不出用 `--map code=税号`。
   2026-09 实跑一份 806 条、120 个编码的清关数据：错误 2 组 7 条、存疑 12 组 294 条、提示 4 组 11 条。

**最终配置再跑 60 条（改写开 + 扩展索引 + 化工章规则，2026-09-16）**：top-1 39（65%）、top-3 45、6 位 41；对照平铺 35：
救 8 坏 4。第一名与改召回之前持平，救回与做坏的名单换了一批（化工混合物、药品、床垫垫等方向错的回来了；平铺候选池
变化又带来 2 条波动）。留一法复核剩下 20 条错：**金标在 40 条候选里的 13 条、不在的 7 条**（改召回前是 8 条）——
召回上限在这批 60 条上只抬了 1 条，与 295 条上 r@40 0.84→0.87 的幅度一致；**现在的瓶颈是判断（13 条候选里有却没挑中），
不是找不到**。注意：不做留一法直接查池子会得到"只剩 1 条不在池"的假数字，因为先例通道会把裁定自己捞回来。
6. **归类要素表**（`attribute_card`，默认开）：归类前先让模型把描述抽成一张固定的表——商品、材质成分、构造工艺、功能用途、
   形态、包装销售、使用者场景、规格，**只填描述明确说了的，没说的进「未提及」**。之后平铺精排与逐级链每一步都带着这张表
   （"未提及的属性不能当作满足"），「未提及」直接并进「需确认」，也就是给客户的问题清单，接到「补充后重跑」。
   单条一次调用、清单一次批量调用，几百 token。归类员本来就是先填这张表再翻税则的。
   **实测（同一批 60 条，对照 42）：表进提示词后 top-1 39、top-3 46，救 2 坏 5，升级行 23 → 31，token 翻倍多**——
   模型看到一串「未提及」后更倾向选兜底品目，方向错反而多了。所以默认 `attribute_card_in_prompt: false`：
   表照抽、「未提及」照进需确认与界面，但**不写进精排与逐级链的提示词**，结论仍是 42 那套。想让它进提示词
   在 `ai_config.json` 里开这个键再测。
7. **清单模式升级行并发**（`guided_parallel`，默认 3）：升级的行此前一条接一条跑，30 行清单升 10 行要 8–10 分钟；
   现在整批进线程池、按完成顺序报进度，墙钟时间约三分之一，token 不变。推理强度 / 超时的上下文在整批外进出一次
   （它改的是共享 provider 的属性，线程里各自进出会互相覆盖）。1 = 串行（测试用）。

**目标怎么定**：60 条金标是 CBP 新裁定的陌生商品、300 字规范英文描述，以此定 8 位第一名 90% 不现实（裁定制度存在的原因
就是它有争议）。现实的三档：前三名含正确答案 85–90%（靠 1、2）；自家重复品类第一名 90% 以上（靠本公司历史申报，
`scripts/eval_company.py --build 200` 在有 MongoDB 凭据的机器上从 products 集合抽金标——它衡量的是"与过去申报一致率"）；
陌生商品第一名 70% 出头，再往上靠补事实。

### 各层要点

- **`term` 是全文检索，不是编码字段查询。** 搜 `8507.60.00` 命中的是正文提到该编码的
  裁定（多为 protest / drawback），不是"归到这个码"的裁定。要找某编码的先例，
  用商品英文名检索再按 `tariffs` 过滤——`precedents()` 就是干这个的。
- **「候选外编码」是归类信号**：CBP 把同类货判到了你没考虑的编码上。标「同品目」的
  与候选同 4 位品目、仅子目不同，最值得先看。
- **引用前必看状态**。裁定会被撤销/修改（实测 `battery` 前 300 条里有 12 条失效）。
  引用一条已撤销的裁定比不引用更糟。模块把三个来源字段归一为「状态」，
  失效的不隐藏但排在后面并标注被谁撤销。
- **多条结论冲突时：HQ > NY，新 > 旧，事实最接近 > 词句最像**。HQ（总部）可撤销
  NY 的裁定，反之不行（实测 2399 条样本里 25 次撤销全部由 HQ 发起）。
  `precedents()` 按现行在前、HQ 在前排序，组内保持 CROSS 相关度。
- **老裁定的 6 位码可能已被 HS 修订改掉**，而 CROSS 不会为此标记撤销——revoked
  只防"结论被推翻"，防不住"编码被搬家"。早于 HS 2012/2017/2022 修订的裁定
  带「版本提示」，引用前须回现行税则核对编码仍然存在。
- **裁定不是保护伞**：只对申请人的该笔交易具法律约束力，他人可参考但货物有差异时
  未必适用——引用前须读全文事实描述段，相似不等于相同，差一个参数结论可能相反。
- 接口公开无需认证，数据属公共领域（data.gov 标注 `usa.gov/government-works`），
  但**无公开文档、无 SLA**。因此本模块超时 10 秒、结果落 `.cache/cross/`（失败也短暂缓存，
  避免离线时每次干等），且**任何失败都返回 `{"error": ...}` 而非抛异常**——
  CROSS 是锦上添花，本地税则查询才是主链路。
- 裁定正文**不做 AI 转述**，只给原文链接。先例的价值就在于它是 CBP 的原话，
  一经转述就不能拿去跟海关讲了。

## 税率引擎说明（v1.2）

**税率形态识别**（`scripts/rate.py` 的 `parse_rate`）：

| 形态 | 示例 | 处理 |
|---|---|---|
| 免税 | `Free` | 等效从价 0% |
| 从价 | `6.5%` | 直接比较 |
| 从量 | `1¢/kg`、`$1.646/kg`、`0.9¢ each` | 需单位货值折算 |
| 复合 | `46.3¢/kg + 14.9%` | 从价部分直接比较，从量部分需折算 |
| 引用 | `The duty provided in the applicable subheading` | 无法折算，标"需人工" |
| 复杂 | `$1.61 each + 4.4% on the case...` | 分部件税率，标"需人工" |

**总税负 = 基础等效从价 + 301 加征 + 附加税**。从量/复合/复杂税在未提供单位货值时标记"需折算"，避免误导。

**搜索匹配**：英文品名精确词 + 前 5 字符词干索引（`battery` 可命中 `batteries`），
多关键词 AND 匹配；同时支持编码前缀匹配（`8507` → 8507 章）。

## AI 功能配置（可选，默认不启用）

AI 层**可插拔**：不配置则 AI 功能返回提示，其余功能（查询/搜索/估算/变动）完全离线可用。
核心查询始终零网络；只有 AI 功能按你的配置访问模型服务。

**两种配置方式（任选其一）：**

**方式 A：Web 端手动配置（推荐）**——打开 http://127.0.0.1:5000 →「AI 助手」→ 右上角 **⚙ AI 服务配置**：
选择服务类型、填 base_url / model / api_key → 保存（立即生效，无需重启）→ 点「测试连接」验证。
api_key 仅保存在本地 `ai_config.json`，界面只显示掩码、绝不回显明文。

**方式 B：直接编辑** `ai_config.json`（项目根目录）：

```json
{
  "provider": "openai_compat",
  "base_url": "https://api.openai.com/v1",
  "api_key": "你的密钥",
  "model": "gpt-4o-mini",
  "temperature": 0.2,
  "timeout": 60
}
```

- `"provider": null` —— 不启用（默认）
- `"provider": "ollama"` —— 本地模型（`base_url` 默认 `http://127.0.0.1:11434`，`model` 如 `qwen2.5:7b`），完全离线。
  可选 `"think": false`（默认）：qwen3 等模型的**思考模式**默认关——本项目每次调用都是按格式出 JSON，
  隐藏推理链只烧时间（实测同一提示开 3.8s / 关 0.2s，搜索页 AI 辅助 27s → 秒级）；要开设 `true`
- `"provider": "openai_compat"` —— 任何 OpenAI 兼容 API：OpenAI 官方（如上例）、DeepSeek（`https://api.deepseek.com/v1` + `deepseek-chat`）、通义千问（`https://dashscope.aliyuncs.com/compatible-mode/v1` + `qwen-plus`）、自建中转站（改 `base_url`）等

其余键：`reasoning_effort`（仅 openai_compat：推理强度 none/low/medium/high…按服务端词表，空 = 不传；实测
gpt-5.6 设 none 每次调用 5s vs 12s、top-3 持平 top-1 低 8 个点）、`num_ctx`（仅 ollama：上下文窗口 token 数，
逐级归类需 ≥ 16384）、`guided` / `guided_threshold` / `guided_max_calls` / `guided_effort`（GRI 逐级归类升级链，
见「GRI 逐级归类」一节，默认关）。推理类模型直连 OpenAI 时若拒绝 temperature / seed，会自动去掉这两个参数重试。

**AI 归类流程**：LLM 提取关键词 → 本地税则库召回候选 → LLM 精排 → 本地引擎校验 301 与税负 →
（可选）低置信度行升级到 GRI 逐级链。
AI 结果仅供参考，正式报关归类以 CBP 裁定为准，请人工复核。

### 自动检测：`scripts/check_sources.py`

```bash
python scripts/check_sources.py                   # 探测三份文件是否有新版本，打印报告；有更新退出码 3
python scripts/check_sources.py --apply --rebuild # 下载覆盖（旧文件备份到 output/sources_backup/<时间>/）并重建数据库
python scripts/check_sources.py --json            # 机器可读
```

- **判"有没有更新"只看内容哈希**：USITC 每次发版都把 China Tariffs 改名（Rev15→Rev17）但内容常一字不变，
  按名判会误报；CSV 导出的换行符会漂，哈希前抹平。版本号 / ETag 只用来省流量（没变就不重下 4MB）。
- 比对对象是**本地文件本身**，手动替换过文件也不会错判。
- htsdata 有更新时报告**行级差异样例**（新增/删除了哪些编码），`--apply` 前先看一眼改的是什么。
- 本地 `China Tariffs_2026HTSRev15.pdf` **文件名不随远端改**（`build_db.py` / `app.py` 按名引用），
  远端版本号记在 `data/.sources_state.json`，Web「📄 查看数据来源」弹窗展示每份文件"与官方一致 / 官方已更新"。
- **局限**：FLIP FRN 的 URL 指向 7-23-26 这一份通知，USTR 若发布**新的**修改通知是新 URL，脚本探测不到，
  需人工关注 [USTR 新闻页](https://ustr.gov/about/policy-offices/press-office/press-releases)（报告里有提醒）。

**定时**：已配 `launchd`（`~/Library/LaunchAgents/com.hts-agent.check-sources.plist`）每天 08:30 跑
`check_sources.py --apply --rebuild --notify`——有更新就**下载覆盖并重建**（旧文件备份到
`output/sources_backup/<时间>/`，`build_db.py` 有产出下限校验，抽不出东西会中止不覆盖旧库；Web 进程按库文件
mtime 热换，不用重启），再弹 macOS 通知，报告追加到 `output/check_sources.log`。2026-09-15 之前只检查不覆盖，
结果 Rev19 出来当天线上还在跑 Rev18。重建后到「数据变动」核对变动清单。下载或重建失败时页头状态胶囊会显示
「官方已更新 …，本地未应用」（`/api/info` 的 `sources_outdated`），此前这个信息只藏在「数据来源」弹窗里。

手动更新（不用脚本）：下载上表三个地址替换对应文件 → `python scripts/build_db.py`。
重建时自动与上一版本对比，生成**数据变动清单**（Web 端「数据变动」可查看），
方便你第一时间发现"客户常查的商品税率变了"。

FLIP 301 豁免的范围限制、页码与 `Ex` 档描述原文（`data/flip301_exemptions.json` 的
`universal_scopes` / `universal_pages` / `universal_ex_desc` 等键）由独立脚本提取：
`python scripts/extract_flip_scopes.py`（FLIP FRN 更新后重跑一次即可），
**改完要跑 `scripts/build_db.py`**——这份 JSON 是编译进 `sec301_db.json` 的，不重建不生效。

## 判定逻辑与重要局限

**判定逻辑**：输入编码取前 8 位 → 在 USTR 清单中查找 → 命中则返回对应 9903 子目及加征比例。

**必须注意的局限（重要）**：

1. **中国 301 的排除（Exclusion）**：已判定，但只有**整号排除**能自动判免（条目正文就是一个统计号，纯粹是编码 + 日期问题）。**按描述授予的排除本工具不自动判免**——同一税号下有的款符合描述、有的不符合，编码本身回答不了，自动判免会直接造出错误申报；工具只给出条目原文与页码，需人工逐条核对。另：排除授予到 **10 位统计号**，只给 8 位时不判免。
   ⚠ 排除有硬到期日：9903.88.69 / .70 均至 **2026-11-09**。**到期日本身不会让工具算错**——有效期按查询当天重算，过期即停止判免、改按满额加征。真正的风险在两侧：① 到期后不重抓，USTR 的延期或新增排除你享受不到，**该免的没免、多缴**；② USTR **提前撤销**某条排除而本地仍按原到期日判它有效，会继续判 0%，那才是**少报**，要被追补加罚。两侧都只能靠 `check_sources.py` 的每日探测兜住，务必让它保持运行；到期前 14 天页面顶栏与探测都会主动告警。
   ⚠ 这与 **FLIP 301 的 ANNEX II 豁免**是两套东西：后者按税号列示、已逐编码判定，带范围限制的会标"范围存疑"（见上表）。
2. **原产地规则**：301 关税仅适用于**中国原产**商品。经第三国实质性转型的产品不适用。
3. **编码版本**：本工具基于 2026 现行 HTS（2022 年后的新编码体系）。旧版编码（如 8703.23.00）会提示"未找到"，请使用现行编码（如 8703.23.01）。
4. **总税率估算**：从价税直接相加；从量/复合税需按单位货值折算（Web 逐行填、命令行传 `--unit-value`），分部件复杂税无法折算，标"需人工"。估算仅供参考。
   ⚠ **总税负不是全部税负**：不含反倾销/反补贴（AD/CVD，按案件与出口商定税，请查 ITA / ACE），不含 Section 232 等按产品触发的 Chapter 99 措施，也不含 note 2 / note 50 等按原产地触发但本工具未建模的标目——后者会按原产地探测并在备注里点名，但法律状态与是否适用要人核实。Special 栏的协定税率只提示不套用。
   ⚠ **数量与单位货值必须按同一个计量单位**：从量税折算走的是 `每单位税额 ÷ 单位货值`，所以单位货值是"每 ‹税则计量单位› 多少美元"。按"件"填一个按 kg 计税的商品，货值与税费会整行算错——Web 估算表已把官方计量单位列出来，按那一列填。
5. **官方口径**：本工具仅供内部效率参考，正式报关以 CBP 裁定和 USTR 官方公告为准。
